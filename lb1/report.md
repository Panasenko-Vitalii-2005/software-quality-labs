# Лабораторна робота №1

## Аналіз якості програмного продукту. Виявлення та документування аномалій

### Мета роботи

Ознайомитися з процесом тестування програмного продукту, навчитися виявляти аномалії у його роботі, документувати знайдені дефекти за допомогою GitHub Issues та визначати їх Severity і Priority.

## Об'єкт тестування

Для виконання лабораторної роботи використано вебзастосунок **SauceDemo**:

https://www.saucedemo.com/

## Середовище тестування

- Операційна система: Windows 11
- Браузер: Google Chrome
- Об'єкт тестування: SauceDemo
- Тип тестування: ручне функціональне тестування

## Базовий сценарій

Для визначення очікуваної поведінки системи було виконано базовий сценарій з використанням облікового запису `standard_user`.

Послідовність виконання:

1. Авторизація в системі.
2. Перехід на сторінку Products.
3. Додавання товару до кошика.
4. Перехід до кошика.
5. Початок оформлення замовлення.
6. Введення даних користувача.
7. Перехід до огляду замовлення.
8. Завершення замовлення.

Базовий сценарій було виконано успішно. Критичних аномалій під час його виконання не виявлено.

### Аномалія №1

Для користувача `performance_glitch_user` після натискання кнопки `Login` спостерігається затримка приблизно 5 секунд перед відкриттям сторінки Products.

Аномалії присвоєно рівень **Severity: Medium**, оскільки основна функціональність залишається доступною, але швидкодія системи погіршується.

**Priority: Medium**, оскільки проблема негативно впливає на користувацький досвід, проте не блокує роботу із застосунком.

Детальний опис та докази наведено у відповідному GitHub Issue.

### Аномалія №2

Під час авторизації як `problem_user` виявлено, що для різних товарів на сторінці Products відображається однакове зображення собаки, яке не відповідає назвам та описам товарів.

Аномалії присвоєно рівень **Severity: Medium**, оскільки дефект порушує коректне візуальне представлення товарів, але не блокує основну функціональність застосунку.

**Priority: Medium**, оскільки дефект суттєво погіршує сприйняття каталогу користувачем, однак не перешкоджає виконанню основного сценарію роботи.

Детальний опис та скріншот наведено у відповідному GitHub Issue.

### Аномалія №3

Для користувача `error_user` виявлено, що кнопка `Add to cart` не працює для окремих товарів. Після натискання товар не додається до кошика, а кнопка залишається у стані `Add to cart`.

Аномалії присвоєно рівень **Severity: High**, оскільки порушено одну з основних функцій інтернет-магазину — можливість додавання товару до кошика.

**Priority: High**, оскільки дефект безпосередньо перешкоджає користувачеві придбати окремі товари та потребує першочергового виправлення.

Детальний опис та докази наведено у відповідному GitHub Issue.

## Контрольні питання

### 1. Що розуміють під якістю програмного продукту?

Якість програмного продукту — це сукупність його властивостей і характеристик, які визначають здатність задовольняти встановлені та очікувані потреби користувачів.

### 2. Чому факт працездатності програми ще не означає її високої якості?

Працездатна програма може містити дефекти, бути незручною у використанні, повільною, ненадійною або не відповідати окремим вимогам. Тому працездатність є лише одним з аспектів якості.

### 3. Що таке аномалія?

Аномалія — це будь-яке відхилення фактичної поведінки програмного продукту від очікуваної поведінки.

### 4. Чому аномалія не завжди є дефектом?

Аномалія може виникнути через неправильні очікування користувача, особливості середовища, некоректні тестові дані або нерозуміння вимог. Тому перед визначенням її як дефекту необхідно встановити причину відхилення.

### 5. Що таке Expected Result та Actual Result?

**Expected Result** — результат, який повинен бути отриманий відповідно до вимог.

**Actual Result** — результат, який фактично отримано під час виконання програми або тесту.

### 6. Які три питання використовуються для формування Title, Expected Result та Actual Result у межах курсу?

Для формування опису використовуються питання:

- **Title:** Що не так?
- **Expected Result:** Як повинно бути?
- **Actual Result:** Як є насправді?

### 7. Для чого потрібен defect report?

Defect report потрібен для документування виявленого дефекту та передачі розробникам достатньої інформації для його відтворення, аналізу та виправлення.

### 8. Яку інформацію повинен містити defect report?

Defect report зазвичай містить назву дефекту, опис або кроки для відтворення, Expected Result, Actual Result, test environment, Severity, Priority та докази дефекту, наприклад screenshot або відеозапис.

### 9. Для чого використовуються GitHub Issues?

GitHub Issues використовуються для реєстрації та відстеження задач, дефектів, пропозицій і процесу їх виконання в межах програмного проєкту.

### 10. Навіщо до Issue додавати screenshot або відеозапис?

Screenshot або відеозапис наочно демонструє проблему, допомагає швидше зрозуміти її та спрощує відтворення дефекту розробником.

### 11. Чим Severity відрізняється від Priority?

**Severity** визначає ступінь впливу дефекту на роботу програмного продукту.

**Priority** визначає терміновість його виправлення.

### 12. Для чого у defect report вказують test environment?

Test environment вказують для фіксації умов, у яких було виявлено дефект: операційної системи, браузера, версії програми, пристрою та інших параметрів. Це допомагає відтворити проблему та визначити, чи залежить вона від конкретного середовища.

## Висновок

Під час виконання лабораторної роботи було проведено ручне тестування вебзастосунку SauceDemo з використанням різних тестових облікових записів. Було виконано базовий сценарій роботи системи та виявлено три аномалії різних типів: проблему швидкодії, візуальний дефект та функціональний дефект.

Для кожної виявленої аномалії створено окремий GitHub Issue із зазначенням середовища тестування, кроків відтворення, очікуваного та фактичного результатів, доказів, Severity і Priority. Найбільш суттєвою виявленою проблемою є неможливість додавання окремих товарів до кошика для користувача `error_user`, оскільки вона безпосередньо порушує основний функціональний сценарій застосунку.
